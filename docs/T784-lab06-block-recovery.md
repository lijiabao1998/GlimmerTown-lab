## 原卡凍結驗收中沒做到的
- 第 3 條「中途斷軌→停在原地→修好→可繼續」：執行期從不讀地格，斷軌只是手動旗標，跟原卡自己的定義不符。
- Chrome 探測結果沒有可核的紀錄。

## 審查找到的缺陷
1. 斷軌標記在 `load`／`newWorld`／`end` 之後仍然留著，漏到下一座城。
2. 第一列還在路上就 `release`，會讓第二列進入同一個閉塞區間；`request('ghost')` 會把路權給一列不存在的車，擋住真車。
3. 跑完的列車永遠不釋放名額，兩趟之後第三列就被拒絕。探測的「第三列被拒」是因為這個 bug 才通過，不是因為同時佔用。
4. 閥門擋不住 break／repair；沒有「未保存」提示。

## 補齊（動手前凍結，之後不改鬆）
- B1：斷軌照原卡定義改成讀真地格。
  - 列車每次要前進，先讀下一格的 `tiles[i].rail`；沒軌 → `track-broken`，列車留在原地；那格重新有軌就能繼續。
  - 純核心的 `breakTile`／`repairTile` 留給單元測試用；執行期的判定一律來自地格。
- B2：讀檔、開新城、`end` 清掉所有列車、等待隊列與斷軌狀態。
- B3：路權規則。
  - 只有登記過的列車（有對應的 054 任務）能 `request`，否則 `unknown-train`。
  - 持有者只有在到站或中止後才能 `release`，路上 `release` 回 `still-running`。
  - 到站或中止的列車自動讓出名額，等待者照 FIFO 取得路權。
- B4：閥門開著時所有變更動作都回 `disabled`；安裝當下就開著 → 整段不安裝（同 T782 B3）。
- B5：面板顯示「未保存」提示，位置不與其他 LAB 面板重疊。
- B6：`vm` 跑執行期那份的測試，接進 `smoke.js`。
- B7：Chrome 探測（固定種子，原生開發者沙盒）：
  - 兩列在同一區間「一列走、一列等」；
  - 第一列中途把它前方一格真軌拆掉 → 停在原地回 `track-broken`；重新鋪回那格 → 繼續到站；
  - 到站後第二列照 FIFO 拿到路權跑完；之後第三列可以開（名額有釋放）；
  - 讀檔清空。
- B8：新斷言故意改壞試過，首紅落在目標。
- 整幀比對、fp、smoke、CI、發布見 T785。
