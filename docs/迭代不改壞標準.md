# 迭代不改壞標準（實驗線版；給 GPT 與所有自主迭代的寫入者）

> 業主 2026-10-10 定：**不管迭代玩法還是美術，都不准迭代壞。** 這份是硬規則，每張卡開工前讀、收工前逐條對（第 8 節自檢清單）。
> 一句話：**每一步都要能證明「沒變壞」；證明不了就停，交給業主，不要繞。**

主線（`lijiabao1998/GlimmerTown`）有同一份標準的主線版（`docs/迭代不改壞標準.md`，主線 T631）；這份把指令換成實驗線的（`smoke.js`、`fp.js`、`probe*.js`、`AUTORUN-LOG.md`）。和 `AGENTS.md`、`AUTORUN.md`、`CLAUDE.md` 一起讀；衝突時以較嚴的為準，拿不準就問業主。實驗線**美術第一**的優先序不變——正因為美術第一，更不准把美術改壞。

---

## 1. 開工前（沒做到就不准動手）

1. 讀：本檔、`AGENTS.md`（誰寫哪裡、分支規則）、`AUTORUN.md`（施工五步、邊界）、`docs/DECISIONS.md`（業主已決定的／待決的）。
2. **先量現況**：改什麼就先量什麼——樣張、數字、`node fp.js --check` 跑一次留底。沒有基準，就沒辦法證明沒變壞。
3. **卡面先推**（`main` 寫入者：`docs/T7xx-*.md`；分支寫入者：`docs/branch/GPT-0xx-*.md`）：目標、**驗收條件（動手前寫好，之後不准改鬆）**、改什麼／不改什麼、回滾方式。
4. **一張卡只做一件事**。玩法和美術不要混在同一張卡。
5. 開工前 `git fetch`，從最新 `origin/main` 開分支；分支寫入者只推自己的分支（寫明兩邊分支名），**不推 `main`、不自己合併**，只有業主點頭才合。

## 2. 玩法迭代不改壞

1. **同種子前後對比**：改到模擬（人口、金錢、電、交通、市民行為）的卡，用同一個種子、同樣天數跑改前改後，數字寫進卡；終點差是混沌雜訊，看短視野配對差。
2. **存檔相容**：舊存檔「載入 → 存檔 → 再載入」所有欄位不變；CI 的冷載入／舊版存檔工作必須綠。存檔格式只准新增可選欄位。
3. **會改變玩家體驗的數字**（價格、上限、容量、速度）**由業主決定**，做兩三檔讓業主挑，不要自己拍板。
4. **每個新效果都掛逃生閥** `window.__noXxx`；**不准用逃生閥或測試開關證明自己沒壞**。

## 3. 美術迭代不改壞

1. **美術定稿權在業主**：新圖先出樣張／對照圖（接觸表最好），業主點頭才接進遊戲；全局觀感（色調、密度、光影、配色、樹種）做兩三檔給業主選，`docs/DECISIONS.md` 已決定的不重問。
2. **只動要改的那幾類**：`node fp.js --check` 其他家族**零變動**；有意改的家族用 `--expect=<家族>` 明列，**不准動 `fp.json`**（合併時由 `main` 寫入者更新）。
3. **每張新圖都要有逃生閥**能即時退回舊圖；**閥關時整幀畫面與改動前逐位相同**。
4. **必看的狀態**（樣張與 CI 真 Chrome 都要涵蓋）：白天、夜裡、冬天（有雪／沒雪）、春夏秋四季色、旋轉四個視角、遠景縮放、地圖邊緣；以及疊在建築上的層——施工、懸停淡出、倒影、行人、煙、夜燈、招牌。
   - 反例（主線 T601 第一版）：公園秋天是綠的、鷹架飄在空中、雪下兩層、碼頭背對真水——全是只看了「白天、正常」造成的。
5. **對標定調**：TheoTown 級密度但分類型不過密；量體高低胖瘦組合；拱形等窗型；變體要**結構差異**，不是換色。

## 4. 量測與效能：先找原因，不要為雜訊造工具

1. 計時異常，**先用最簡單的 A/B 確認是不是真的**：新舊交錯量、比中位數與 p90、每組 ≥30 樣本；排除已知、與改動無關的週期性成本。確認是雜訊就修判準，**不要為雜訊造追蹤基礎設施**。
   - 例（主線 T626）：讓主線變紅的「暖畫 p95」實際新舊中位數 2.5 對 2.6 毫秒；那個約 12 毫秒的尖峰是水面每 32 次重畫換一幀、整張地面重建。
2. **同一個問題，診斷卡最多連開 2 張**；第 3 張之前必須把已有數據和選項交給業主決定。
   - 反例（主線 T604–T625）：連開 20 多張診斷卡追「手機夜景重畫」，每張都死在量測工具本身（追蹤檔超過上限、CPU 剖析時間戳負值、視窗高度改變），一次都沒量到瓶頸；新圖其實沒有讓重畫變慢。
3. GitHub macOS 跑機的計時**只當參考、不當擋門**（同一份程式一過一不過）。
4. 效能問題先問「玩家感覺得到嗎」：第一幀卡頓、持續掉幀才是問題；單次尖峰不是。

## 5. 守衛要守對東西

1. 每個自檢／像素守衛寫清楚「它擋什麼壞法」，並用**故意改壞一處**證明：**第一個紅燈必須落在目標守衛**。
2. **不准拿被測的東西當標準答案**（循環判斷）：期望值要從獨立來源來——直接烘焙、規格副本、git 物件、線上實物。
3. 只有原文比對、沒有行為檢查的守衛不算數。
4. **判準放寬一定寫在卡面**：寫明放寬什麼、理由、放過多少。
5. 自檢掛進 `smoke.js`、像素守衛寫成 `probeXXX.js`；不能在本機跑的（GPT）標「未跑，待合併者跑」，不准寫成通過。

## 6. 發佈不改壞

1. **`main` 隨時要綠**；分支 CI 綠了才開 PR。紅了先查原因、修好；**不准帶紅開 PR、不准用重跑賭過**。
2. 分支寫入者不改 `GAME_VER`／`GAME_ANCHOR`／開始畫面版本字、`AUTORUN-LOG.md`、`fp.json`、`docs/DECISIONS.md`（合併時由 `main` 寫入者統一改）。
3. 網站（GitHub Pages）只從綠的 `main` 部署；合併後確認部署工作綠，並開真網址看一眼。
4. 不准 `--force` 推 `main`；推錯就停手、寫進卡、告訴業主。

## 7. 停手與回報

1. **同一件事試 2 次沒進展就停**：寫清楚卡在哪、試過什麼、有哪些選項，交業主。
2. **沒跑過的不寫「通過」**；失敗照實寫；「沒做成的事」不准空著、不准美化。
3. 每張卡收工給業主四行內的結論：做了什麼、怎麼證明沒壞、還剩什麼、要業主決定什麼。

## 8. 收工自檢（逐條打勾才准開 PR／推 `main`）

- [ ] `node fp.js --check` 只有明列的家族變；逃生閥關時整幀相同
- [ ] 美術：日／夜／冬（雪有無）／四季／旋轉／遠景／地圖邊緣／疊層都看過，對照圖在卡裡
- [ ] 每條新守衛都故意改壞試過，首紅落在目標
- [ ] `node smoke.js` 連跑 3 次全綠（或 CI 綠，附連結）；沒有靠重跑
- [ ] 卡上沒有任何「通過」是沒跑過的
