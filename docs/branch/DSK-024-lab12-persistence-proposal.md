## 3. 提案（三段式，任何一段都要業主點頭）

### 3.1 最小持久化面

只新增**可選欄位**、只放在存檔根的 `lab` 命名空間：

```json
"lab": {
  "schema": 1,
  "shadowLedger": { "batches": 0, "events": 0 },
  "lastDelivery": { "batchId": "string", "day": 0, "status": "UNLOADED" } | null,
  "flags": { "enabled": false }
}
```

規則：
- **只允許新增**；不改任何既有欄位、不改既有 writer 的輸出順序。
- `schema` 遞增；舊存檔沒有 `lab` → 當 `null`，不補預設、不觸發遷移。
- 讀到不認識的 `schema` 版本 → 保留原值不動、把 `lab` 標成 `readOnly`，**不覆寫**。

### 3.2 讀寫邊界

- 寫：只在玩家明確「開始／結束一趟影子配送」時寫一次（不是每 tick 寫）。
- 讀：載入時只還原 `lastDelivery` 的顯示狀態；**不重播事件、不重建批次**（避免「假稱恢復舊運輸」，那是 T777 明文禁止的）。
- 任何寫入失敗（quota、例外）→ 回滾到寫入前字串，遊戲照常跑，只在面板顯示「未保存」。

### 3.3 驗收（如果哪天實作）

1. 舊存檔（無 `lab`）載入 → 存檔 → 比較：除新增 `lab` 外**逐欄位不變**。
2. 新存檔（有 `lab`）載入 → 存檔 → 再載入：`lab` 逐位元不變。
3. 未知 `schema` → 不覆寫、不崩潰、面板顯示唯讀。
4. `node smoke.js` 3 連綠、`node fp.js --check` 零變動（fp 不受影響）。
5. 故意改壞 `lab` 一處 → 首紅落在對應守衛（不是 `catch` 吞掉）。
