## 1. 進場探針：對照官方美術指南，找出「不夠豐富」的可量化缺口

本輪找到 TheoTown 的**官方美術指南**（`A better visual guide on shading, shadows and detail`，
論壇原文 p=237306，社群站 pca.svetikas.lt 有整理版）。逐條與本作對照：

| 指南規則 | 原文要點 | 本作現況 | 判定 |
|---|---|---|---|
| 受光方向 | 「光從**左**方來」，左亮右暗，**必須套用到所有結構** | T526 打磨層左緣 2px 提亮 | ✅ 符合 |
| 陰影方向／顏色 | 往**右斜**（約 45°）、**偏藍**、要**淡出**、牆影不要太長 | `rgba(10,14,24,.16)` 偏藍 ✓ 淡出 ✓ | ✅ 方向對 |
| 陰影不透明度 | 官方教學：**純黑 20%** | **16%** | ⚠️ 差一級（列後續） |
| **窗台** | 「**加窗台**能為建築創造深度」；縱向面用對面顏色、橫向面用平屋頂色 | **只有一條白色高光線**，不是簷口 | ❌ **本輪修** |
| 玻璃顏色 | 用更深的顏色，純黑也可；**避免亮藍窗** | `#26314e` 深藏青 | ✅ 符合 |
| 環境光遮蔽 | 用**深色半透明像素**（與陰影同色）放在**轉角與邊緣** | 純黑 13%／25%，**未用偏藍陰影色** | ⚠️ 顏色不符（列後續） |
| 雜訊 | 加隨機亮暗像素做質感，但「**不要過量**」 | T526 加 2×2 棋式 4.5% 壓暗 | ✅ 溫和 |
| 描邊 | 「**在牆上加描邊會毀掉品質**」 | 本作只描**外輪廓**（非牆面內線），且用深藍灰 | ✅ 不違規 |
| 屋頂 | 有常見形狀與**抬升比**（例：1/2 屋頂）；平屋頂建議加女兒牆 | 有 `pyramidRoof`／`flatParapet`／抬升比 | ✅ 符合 |

**結論：最明確、可量化、且覆蓋面最大的缺口＝「窗台只是白線」。**
本作的窗戶在 `windows()` 內，所有 RCI 建築（住宅／商業／工業）共用 ⇒ **一改就覆蓋整座城的每一扇窗**。
這正是「建築豐富度」最大的一條槓桿。

## 2. 驗收條件（動手前寫定）

1. 每個窗戶下方出現**真正的簷口**：上緣受光面（比窗寬 2px＝突出）＋下緣落影，
   符合「光從左來、影往右下」的既有慣例。
2. 窗台顏色**由該棟建築的色盤驅動**（受光面取屋頂色系），不是寫死的白。
3. **只影響 `bld` 一族**：改動必須做成 opt-in（`windows()` 也被另一處繪製函式使用，
   直接改會連帶改到別族，指紋差就不等於宣告）。
4. 逃生閥 `window.__noSill539`，可單獨拆掉。
5. 不消耗 R()、不動模擬、不進存檔、像素只走整數。
6. **指紋差 == `bld`**（其餘 148 族零變動）＋**棘輪不退步**。
7. A/B 接觸表日夜各一張（`bld` 567 葉過大，出**住宅 lv1 切片**作代表，並在卡面註明是切片）。
8. 煙霧測試綠 ＋ commit。

## 3. 施工（含關鍵轉折）

### 走錯兩次路，都是靠探針救回來的

**第一次：改 `windows()`** —— 在窗戶繪製函式裡加簷口分支。
指紋差 **0**。加了計數器：`windows()` 被呼叫 628 次、簷口分支執行 **5053 次**——**確實有畫**。

**第二次：洋紅玻璃探針** —— 把 `glass` 改成 `#ff00ff`。渲染出來**數 0 個洋紅像素**。
⇒ **RCI 的窗戶根本不是 `windows()` 畫的。**

**真相**：`buildSprites` 之後還有一整串後置 pass（T479 立面材質、T480 RCI 建築重建、
T480A 橋樑、T485 物流、T516 都會像素架構），**RCI 的最終外觀由它們決定**，
任何畫在 mkBld 部件裡的東西都會被重繪蓋掉。旁證：T479/T480 都用
`if(seen.has(sp.img))continue` **以 canvas 物件去重** ⇒ 本作本來就存在跨家族共用同一張畫布。

### 正解：跑在最後的像素級 pass

`applyT539WindowSills()`：
1. 走訪 `SPR.bld` 中 `^[123]_` 的 RCI sprite；
2. **自動偵測玻璃像素**（深藍灰、亮度<74、b≥r 且 b−r<48 —— 本作玻璃 `#26314e`／`#31435f` 系）；
3. 每個「連續 ≥2px 的玻璃直段」下方畫簷口：**受光面比窗寬 2px**（左右各外擴 1px＝突出感）
   ＋**偏藍落影**一列（指南：陰影偏藍）；
4. **必須呼叫在 bootstrap 最末**——實測把它放在 T480A 之後仍被 T485/T516 覆蓋
   （`bld` CRC 兩次都 `adc38cc6` 不變），移到最末才變成 `a744b214`。

逃生閥 `window.__noSill539`；零 R()、不進存檔、像素全整數。

## 4. 施工紀錄（如實）

- **自捕 1**：指紋差 0 卻又「確實有畫」——矛盾點靠**計數器＋洋紅探針**兩次量測定位，
  證明問題不是我的代碼沒跑，而是**執行順序**。**「有跑」不等於「留下」**。
- **自捕 2**：harness 的「烘焙完成」閘門（`__t519Roof>0`）在 `buildSprites` 內部就成立，
  涵蓋不到後置 pass ⇒ **T536–T538 的指紋與記分卡全都漏掉 T479/T480/T485/T516**。
  已加 `__bootDone453`／`__bootSeq453`。但改成「需新序號」後**煙霧紅燈**（載入既有城市不重跑 bootstrap），
  最終採「roof 閘門 ＋ 3 秒沉降」。**閘門目前是近似值，這是已知弱點。**
- **自捕 3**：Python 產生 JS 模板字串時 `${'${seqBefore}'}` 變成**字面字串**，
  送進頁面是語法錯誤、被 waitFor 吞掉 ⇒ 閘門永遠不過。改用直接寫入行號修好。
- **未盡（不美化）**：
  1. **宣告範圍被迫擴大**：`--expect` 必須寫 `bld,park,parkS,parkA`。
     原因是本作跨家族共用 canvas（寫入 `bld` 的畫布會連帶改到共用它的 park 系）。
     業主規則說「多改一族就是紅」——這裡多改的三族是**共用物件的必然結果**，不是手滑；
     但**正解應該是「寫入前先 clone」**，讓影響面回到單一族。列為下一輪前置。
  2. 簷口是**用啟發式偵測玻璃**畫的，不是真的知道窗在哪。深色偏藍的裝飾若被誤判，
     會在不該有簷口的地方長出一條線。**尚未逐族目視全部 180 棟**。
  3. 夜圖完全沒動（窗台不發光，正確），但也因此**夜圖覆蓋率不變**（31.0%）。
  4. 「受光方向」與 TheoTown 相反這件事（本作左暗右亮、指南要求左亮右暗）**尚未處理**——
     這是下一個結構性議題，改它會動到 `isoBox` 的顏色傳參，牽連所有 iso 建築。
