# T746 — CI 加固：style.json 不准手改、Pages 只部署本倉庫 main 的推送

**輪次**：r193
**基線**：T744、T745 之後
**狀態**：施工中（卡面先推佔號）
**業主決定**：2026-10-14「123 美術和規則全部你決定」。來源是 T744 的獨立審查：GPT 要無人看管地連續迭代，下面兩個洞不能靠規則自律。

---

## 1. 這一輪要解決什麼

1. **`style.json` 可以被手改來關掉棘輪。**
   - `fp.js --check` 的風格棘輪只擋「這次算出的分數比 `style.json` 低」。
   - 有人把 `style.json` 的分數改低（或整族刪掉）就能過關，合進 `main` 之後往後的棘輪都從低點起算。
   - 規則要求 GPT「逐位元原封不動提交 CI 給的新基線」，但沒有任何檢查。
2. **`pages.yml` 可能部署 fork 的程式碼。**
   - Pages 由「煙霧工作流跑完」觸發，條件只有 `branches: [main]` 與「結論 success」。`branches` 比對的是觸發那次 run 的分支名。
   - 這是公開倉庫：有人從 fork 開一條叫 `main` 的分支發 PR，煙霧對 PR 跑成功，就可能觸發 Pages，而 `pages.yml` 會 checkout 那次 run 的 commit（fork 的）去部署。
   - 這個洞在 T742 之前就存在，T744 審查時發現。

## 2. 改什麼／不改什麼

- **`fp.js`**：`--check` 時，倉庫 `style.json` 每一族的內容（總分、七軸、葉子數、原始計數）都要等於這次算出的；不同就紅，並列出哪幾族。寫入模式不受影響。
- **`pages.yml`**：自動部署的條件加上「觸發的那次煙霧是 push 事件」且「來源倉庫就是本倉庫」。手動觸發照舊（業主或 main 寫入者用；GPT 不准，規則已寫在 T744）。
- **不改**：遊戲檔、`fp.json`、`style.json`、其他判準。

## 3. 怎麼算做完（動手前寫下，之後不改鬆）

1. 本機：原樣 `node fp.js --check` 綠（倉庫的 `style.json` 就是算出來的那份）。
2. 故意改壞（倉庫複本）：把 `style.json` 裡 bld 的總分改低 →
   - 修前 `fp.js --check` 綠，證明洞存在；
   - 修後紅，紅項寫 `style.json` 與這次算出的不同：bld。
3. 故意改壞②：刪掉 `style.json` 裡一整族 → 修後紅。
4. CI 手動觸發 session 分支：`fp` 綠（跑機算出的 `style.json` 與倉庫一致）。
5. `pages.yml` 語法正確；推 main 後，main 的推送照常觸發 Pages 並部署成功。fork 的情況無法在這裡實測，照實寫。
6. 煙霧 3 連綠（產品沒改，照流程跑）。
