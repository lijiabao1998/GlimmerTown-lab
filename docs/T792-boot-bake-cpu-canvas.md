## 原因（進場量測，2026-11-12～13，v14.77／`02eaa5f`）
量測條件：業主的筆電（Intel Arc 140V，螢幕 2880×1800），無頭 Chrome 157 開真顯示卡（`--use-angle=d3d11`），畫布 2828×1600。倉庫現有的量測（`bootperf.js`、`perf.js`、煙霧、CI）都是 `--disable-gpu`、1280×800，看不到下面這些。

| 項目 | 量到的 |
|---|---|
| 開機到主選單 | 真顯示卡 56–74 秒（機器忙時 85–196 秒）；同一台機器無顯示卡 31 秒 |
| 開機完記憶體 | 顯示卡行程 2,660 MB＋頁面行程 895 MB |
| 開機期間的像素讀回 | `getImageData` 13,708 次、`putImageData` 14,356 次，共約 4.97 億像素 |
| 2D 畫布第一次取得 context 的時機 | 開機前 3 張（`#game`、`#titleBg`、`#mini`）；開機期間 15,592 張，其中 216 張本來就帶 `willReadFrequently`；13,708 次讀回全部落在開機期間建立的畫布上 |
| 開機完還活著的畫布 | 7,459 張，原始像素 593 MB |
| 正常城市（`docs/branch/GPT-022-guard-inputs/native-city-mature36-021.json`，425 棟）預設縮放正午 | 8–18 fps（隨機器當時多忙） |

- 原因：Chrome 有顯示卡時，2D 畫布預設放在顯示卡上。烘焙每讀回一次像素，都要跨行程等顯示卡；幾千張精靈各佔一張顯示卡貼圖。
- 實驗（只在量測頁面注入，倉庫沒改）：讓開機期間建立的畫布帶 `willReadFrequently`：
  - 開機 28–39 秒；記憶體約 1.65 GB；
  - 兩組同時對照（兩個 Chrome 同一時刻量同一場景，啟動順序對調）：正午預設縮放 19.7／19.9 對 11.6／10.9 fps，午夜 14.2／14.7 對 9.1／10.0 fps，七個場景全部較快。
  - 對照實驗：所有畫布都帶（含每幀用的暫存層）反而變慢，所以範圍只限開機期間。
